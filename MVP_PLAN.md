# План реализации MVP Tandelo

## Цель

Довести базовый self-hosted CRM workflow до рабочего состояния и описать в README только существующие функции и подтверждённый MVP scope. Интеграции, plugin SDK и AI не входят в MVP.

План реализован: добавлены аналитика воронки, управление задачами из списка, создание и управление пользователями и группами, а также RBAC-проверки API. E2E-сценарий RBAC добавлен; для его запуска нужны работающие API и PostgreSQL.

## Решения для MVP

- Роли фиксированные: `Admin` и `Member`. Произвольные роли не создаются из приложения.
- `Admin` имеет полный доступ. `Member` может читать и менять лиды, контакты, компании и задачи; читать аналитику, воронки, кастомные поля и справочники пользователей/групп. Управление доступом и группами доступно только `Admin`.
- Группы служат для организации пользователей и не задают видимость CRM-записей.
- Задача всегда связана с лидом. Связи с контактами или компаниями нет. Ответственный необязателен.
- Первый пароль пользователя задаёт `Admin`. Приглашения и сброс пароля по email не входят в MVP.
- Поддерживаемый путь запуска: локальный web/API и PostgreSQL в Docker Compose. Производственные образы, оркестрация и другие базы данных остаются на потом.

## Этапы

### 1. Роли, permissions и защита API

- Расширить каталог разрешений ресурсами задач, воронок, кастомных полей, аналитики и групп.
- Идемпотентно создавать разрешения и две системные роли, используя существующие таблицы `roles`, `permissions` и `role_permissions`.
- Добавить permission decorator/guard и назначить read/write проверки всем защищённым контроллерам. Login и health-check остаются публичными.
- `Admin` получает все MVP permissions. `Member` получает read/write для leads, contacts, companies и tasks, read для analytics, pipelines, custom fields, users и groups. Изменение users/groups и чтение фиксированных roles доступны только Admin.
- Фиксированные роли read-only через API: Admin назначает их пользователям, но не создаёт и не редактирует роли.
- Проверять активность пользователя при login и при каждом запросе с JWT. Не позволять удалить или отключить последнего активного Admin.
- Ограничить назначения пользователей одной из двух системных ролей; не предоставлять API-операции редактирования системных ролей.
- `db:seed-admin` должен назначать создаваемому пользователю роль `Admin`. Seed разрешений и ролей должен безопасно повторяться и не зависеть от наличия демо-лидов.

### 2. Управление пользователями и группами

- Подключить кнопку создания пользователя к существующему `POST /api/users`. Форма принимает имя, email, начальный пароль, одну системную роль и необязательные группы.
- В существующей форме редактирования оставить изменение имени, email, роли и групп; добавить включение/отключение пользователя и администраторский сброс пароля.
- Добавить экран групп с созданием, переименованием и удалением. Назначение группы пользователям оставить в форме пользователя.
- Ограничить административные действия на API, а не только скрытием элементов интерфейса.
- Добавить `GET /api/auth/me`, возвращающий текущего пользователя и список его effective permissions. Использовать его для скрытия административных пунктов меню; серверные permission checks остаются обязательными.

### 3. Управление задачами из общего списка

- Подключить кнопку `Task` на странице Tasks к форме создания задачи.
- Обязательные поля: лид, тип, текст и срок. Ответственный необязателен. Связь сохраняется через существующий обязательный `leadId`.
- Добавить действие завершения/повторного открытия задачи в таблице. Сохранить создание и отметку выполнения из карточки лида.
- После создания или изменения синхронизировать список и показать ошибки API, пустое и загрузочное состояния.

### 4. Базовая аналитика

- Добавить read-only endpoint `GET /api/analytics/pipeline` с количеством лидов и суммой `price` по pipeline/status.
- Реализовать экран Analytics с выбором воронки и итогами по стадиям. Проверить доступ Member на чтение.
- Не добавлять временные графики, конверсию и экспорт.

### 5. README и первый запуск

- Описать текущее состояние CRM и этапы MVP без заявлений о работающих интеграциях, SDK или AI.
- Удалить формулировку о задачах, связанных со сделками и людьми. Описать задачи как связанные с лидами и ответственными.
- Заменить диаграмму интеграционного слоя схемой Angular → NestJS API → PostgreSQL и текущих backend-модулей.
- Перенести интеграции, plugin SDK, адаптеры, автоматизации, AI и расширенную аналитику в Roadmap.
- В Quick Start описать `.env`, `JWT_SECRET` не короче 32 символов, запуск PostgreSQL, миграции, необязательный demo seed, создание администратора и запуск API/web в отдельных терминалах.
- Добавить команды web и API e2e; пометить Quick Start как локальный development setup.

## API и интерфейсы

- Новый API: `GET /api/analytics/pipeline`, read-only агрегация по воронкам и стадиям.
- Новый API: `GET /api/auth/me` возвращает безопасные данные текущего пользователя и effective permissions для интерфейса.
- API задач сохраняет обязательный `leadId`; миграция схемы для задач не нужна.
- Использовать существующие группы и таблицу `role_permissions`; миграция нужна только если при реализации обнаружится отсутствующая таблица или обязательное ограничение целостности.

## Проверки и критерии готовности

- На чистой базе после миграции seed можно повторить без дубликатов; `db:seed-admin` создаёт активного пользователя с ролью Admin.
- Admin проходит все проверки доступа. Member может работать с CRM, но не может создавать пользователей, менять группы или читать/менять системные роли. Неактивный пользователь не может войти; ранее выданный JWT больше не даёт доступ.
- Создание задачи без лида отклоняется; задачи из общего списка и карточки лида отображаются с ответственным и состоянием выполнения.
- Количества и суммы аналитики совпадают с лидами по стадиям; пустая воронка отображается без ошибки.
- Quick Start с новой `.env` приводит к доступному web, API и первому входу администратора.
- Добавить целевые unit/e2e сценарии для RBAC, сидинга, задач, групп и аналитики. Проверить затронутые Nx test/e2e, lint и build targets; полный прогон выполнять только при необходимости.
